CSR message "attachments" that are telephony **live-call recordings** (`audio/aac`, e.g. `liveCall_*.aac`) cannot be played OR downloaded: BC's own IIFE issues `GET /api/attachment/download?attachmentId=…&clientId=…&apiId=…` → **404, body "Attachment file not found."** Re-confirmed 2026-07-27 on deployed build `csrWrapper:develop_20260722` (repro: contactMessageId `6a6796cd8fc146711b11455c`, attachmentId `6a6796c78fc146711b114553`). First seen 2026-06-26 (attachmentId `6a3d7295d2a2310fd7ef9ed9`).

**Our wiring is CONFIRMED CORRECT (definitive, TASK-1 answer):**
- `EmailTicketsPage` renders `selected.attachments` where `selected` is a contactMessage doc from `adminFindContactMessages` → `api.message.contact.find` (`GET /contactMessage/admin/find`). It picks `att.id || att.attachmentId || att._id || att.attachment_id` — covers every plausible BC field name.
- BC contract (`csrApi v3.csv:2338-2340`): download `attachmentId` = the id in the `[Attachments]` of a Find-User-Contact element. There is ONE stored attachment-object id per file; `contact.find`, `contact.histories`, and `user.findUserContacts` all return the SAME contactMessage docs from the SAME collection, so the id from find/histories IS the download attachmentId. No per-endpoint id mismatch exists.
- Airtight proof (pure code-trace, no error-string parsing): `EmailTicketsPage` passes `att.id` **unmodified** to BC's own `attachment.download`; the captured GET shows `attachmentId=6a6796c78fc146711b114553` = exactly what `att.id` resolved to, and **BC's OWN IIFE** issued that request. We forward the exact id BC's find-response put on the attachment, through BC's own code. Whether that id matches what BC's download endpoint expects is a question of BC internal consistency — we can only send what BC handed us. (Do NOT lean on the "Attachment **file** not found" wording as a record-vs-blob discriminator: the same telephony recording returned "attachment not found" WITHOUT "file" on 2026-06-26, so BC just reworded — it doesn't prove the record resolved.)

**playAudioFlag mechanics (corrected, verified against `develop_20260722` handler):** handler does `const {playAudioFlag:n, ...o}=e; GET {params:o}` — so playAudioFlag is stripped from the **server GET** (correct), then RETAINED: `if(n && isAudio) getAudioByBlob(blob) else <a download>`. So play vs download is a **client** branch on the SAME blob → **play and download hit the identical server request**. A 404 blocks BOTH. playAudioFlag CANNOT rescue a 404ing recording. (ASK D's "playback ✅ via playAudioFlag" applies only to CSR-uploaded audio that returns a blob, NOT telephony recordings.)

**Why the 404 (candidates — can't disambiguate read-only):** telephony recordings carry parent-message `brandId:"unknown"` (apiId `cli`/clientId `curl`, `liveCallId`); either `/attachment/download` brand-scopes its lookup and excludes them, OR the recording file was never persisted / purged by a retention window. Cannot confirm read-only whether the file exists — so the ask must include a persistence/retention question, not assume "file exists but brand-scoped". NOT a bucket-name issue (`bucketName:"attachments"`, same as normal). Live-call recordings are documented NOWHERE in the CSVs; no `liveCall.*`/`recording.*` method exists in the IIFE — `/attachment/download` is the only file path.

**403 on Find-User-Contact:** `csrFindAllUserContacts` → `POST /database/search {collectionName:'userContact'}` → 403. Permissions/collection-access denial (CSR role can't query userContact via /database/search). ORTHOGONAL to the 404 — the failing attachment comes from `contactMessage` (contact.find), which loads fine; the 403 is a tolerated SECONDARY source (allSettled). Does NOT block getting a download-valid attachmentId.

**How to apply:** BC-side fix, NOT ours. Already logged as **ASK D** in `docs/BC_CSR_ASKS_PACKAGE.md` (+ userContact 403 elsewhere in same doc). Two-path ask: (a) BC fixes server-side retrieval for `brandId:"unknown"`/telephony attachments, or (b) BC names the real discriminating param (bucketName/brandId empirically dead — both returned 404) and we forward via the `...o` params spread — no IIFE change. See [[csr-attachment-download]].
