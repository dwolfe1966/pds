IDLookup.AI React Front-End & API Specification for Cursor.ai 
Introduction 
IDLookup.AI helps users find public information about people and monitor when others search for them. The frontend will be a single-page React.js application (HTML, CSS, JS) and will call a back-end API layer implemented by a colleague. The goal of this specification is to define the signup funnel, member experience, API endpoints and authentication model so that Cursor.ai can implement the React front-end consistently and the back-end team can supply the necessary endpoints. 

General Design Principles 
1. 
Clear value proposition – On the landing/search page and signup screens, clearly state what IDLookup.AI does and why the user should continue. Users decide whether to sign up based on this messaging . 

2. 
Minimal forms & progressive profiling – Ask for only essential data in the first step. Additional details can be requested later via progressive profiling to keep friction low 

3. 
Responsive and accessible design – The interface must work on desktop and mobile. 

Mobile-optimization is critical because more than half of internet traffic comes from mobile devices . Use semantic HTML and ARIA attributes for accessibility. 

4. 
Consistent dashboard design – Dashboards should present relevant information at a glance, use big bold numbers and ample white space 
, and follow F- and Z-pattern scanning to guide the user’s eye 
. Group related data into cards/panels and allow users to drill down for details 
. 

5. 
RESTful, versioned API – All endpoints are under /api/v1/… . Versioning from day one prevents breaking changes 
. Use nouns for resources, HTTP verbs for intent, and proper HTTP status codes 




. Implement pagination, filtering and caching to handle large data sets 
.

Page Categories & Navigation 
IDLookup.AI serves three distinct groups of users, each with its own set of pages and navigation menus: 
1. Sales Pages (public) 
These pages are accessible without authentication: 
• 
Home, About & Contact – Explain what the service does, highlight the value proposition and provide a contact form for inquiries. The home page is the entry point for organic visitors and should feature a clear call-to-action . 

• 
Search landing pages – When a user arrives from an ad campaign with a query (name, email, address or phone), they see a pre-populated search bar and a list of public search results. They can click a result to view a truncated preview. 

• 
Logged-out search results & detail preview – Provide enough information to interest the user but blur sensitive data until they sign up. 

• 
Sign up / login – A progressive sign-up funnel with account creation, email verification and payment capture, as described under “Sign-Up Funnel.” A separate login page allows returning users to authenticate. 


Navigation: Sales pages share a simple top navigation bar that includes the logo on the left and links to Home, About, Contact, and Sign Up / Login. On search results pages, show a secondary bar with the search form and a button to sign up or view membership benefits. Keep navigation minimal to focus the user on conversion 

2. Member Pages (authenticated) 
Once a user has signed up and logged in, they access member-only pages: 
• 
Dashboard – The home screen showing “Who searched for you,” recent activity, alerts summary and subscription status as described in the “Member Dashboard” section. 

• 
Profile – Allows the member to view and edit their information. 

• 
People search & results – A more powerful search interface with filters and the ability to view full reports. 

• 
Search result detail/report – Displays detailed information for a person, including contact info, relatives and associated records. 

• 
Who is searching me – A list of search events where others looked up the member. 

• 
Alerts – Manage search alerts. 

• 
Account/Billing – Manage subscription and payment information. 

• 
Settings / Security – Manage password, MFA and privacy settings. 

• 
Logout – End the session. 


Navigation: Member pages use a persistent navigation bar (e.g., sidebar or top bar) tailored to authenticated users. It contains links to Dashboard, Profile, Search, Who Is Searching Me, Alerts, Account and Logout. The nav highlights the current section and collapses or hides items on mobile for responsiveness. Role-based rendering ensures members do not see admin links 




3. Admin Pages (internal) 
Administrators and customer-service representatives have additional pages to manage the platform: 
• 
Users – View and search all user accounts. Provides list with filter/search, ability to suspend or delete accounts. 

• 
User detail & history – Drill-down page showing a user’s profile, history of searches, login sessions, alerts and subscriptions. 

• 
Sessions – List active and past sessions for auditing and security. 

• 
Purchases – View all purchases/subscriptions. A purchase detail page shows payment info and invoice status. 

• 
Data removal – Manage requests from users to remove their personal data (for GDPR/CCPA compliance). 

• 
Analytics – Visualize site metrics, search volumes, conversions, churn and other KPIs. Use charts and dashboards designed per F- and Z-pattern scanning 
. 

• 
CS rep management – Manage customer-service agents, assign roles and monitor performance. 


Navigation: Admin pages display an admin-specific navigation bar, typically a sidebar with links to Users, Sessions, Purchases, Data Removal, Analytics and CS Rep Management. The nav may be collapsible to maximize workspace. Only users with the admin role should access these routes; ensure proper role checks in the front-end and API.

Authentication Model 
IDLookup.AI will use token-based authentication with JSON Web Tokens (JWTs). Upon successful login, the server issues an access token with a short expiration (e.g., 15–30 minutes) and a refresh token with a longer expiration (e.g., 7 days). The React application sends the access token in the Authorization 
/refresh-token 
with the refresh token 
header for each request. When the access token expires, it calls to obtain a new access token. 
Token Storage & Security Considerations 
• 
Preferred method – HttpOnly cookies: Store the refresh token in an HttpOnly cookie with the 

Secure flag and optionally SameSite=strict to prevent XSS and CSRF attacks 
. Cookies adhere to the same-origin policy and support setting expiration dates, making them well-suited for long-lived tokens 

• 
Access token storage: Save the short-lived access token in browser memory (e.g., React state or a context provider). This avoids persistent storage and reduces the risk of token theft if a third-party script is compromised 
. When the page is refreshed, use the refresh token cookie to obtain a new access token. 

• 
Alternative – sessionStorage/localStorage: If you choose to store tokens in web storage for convenience, consider encrypting them and setting short validity periods 
. However, storing JWTs in localStorage exposes them to XSS attacks 
. Using secure cookies is preferred for persistence 



. 
• 
Short validity & refresh: Set a short lifespan for access tokens and implement a refresh mechanism to reduce the window of opportunity for attackers 
. Use refresh tokens that can be rotated and revoked if suspicious activity is detected. 

• 
Role-based access control: Include user roles in the JWT claims. On the client, use conditional rendering to show or hide features depending on role (e.g., admin vs. regular user) 

• 
Email verification: Require users to verify their email addresses before granting full access. This step helps ensure a higher-quality user base and reduces spam signups 




Form Handling & Validation 
• 
Use controlled React components for all forms and handle state via React Hooks. Provide inline validation and helpful error messages. Do not submit the form until validation passes. 

• 
Display password instructions near the password field and provide real-time feedback on strength . Include a show/hide password toggle 
.

• 
After a server error (e.g., email already registered), display the server’s error message using the standardized error envelope.

Error Handling & Feedback 
• 
Show loading indicators during network calls. 

• 
Use toast notifications or banners to display success (e.g., “Alert created”) or error messages (e.g., “Payment failed”). 

• 
Catch network errors and unexpected exceptions and show a generic error page with contact support information. 



Security & Privacy Measures 
• 
Use HTTPS for all network communication. 

• 
Sanitize user input on the client and server. Escape HTML to prevent XSS. 

• 
Implement CSRF protection when using cookies for authentication (the SameSite flag and anti-CSRF tokens). 

• 
Comply with data protection regulations (e.g., GDPR/CCPA): provide a privacy policy, allow users to request data removal and implement appropriate consent flows. 



Conclusion 
This specification describes the complete user journey, UI components, API contracts and authentication model for IDLookup.AI’s React front-end. By following the best practices—minimizing sign-up friction , using progressive profiling 
, designing dashboards that highlight key data 
, implementing RESTful versioned APIs and storing tokens securely 
—the IDLookup.AI platform will offer a smooth, secure and user-friendly experience. Cursor.ai can implement these guidelines to build the front-end while coordinating with the back-end team to expose the described endpoints.
